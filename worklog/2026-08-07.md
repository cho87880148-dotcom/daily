## 1. 원인 ① — 30분마다 도는 예약이 사실상 안 돌았다 (확인됨)

GitHub Actions 실행 기록을 API 로 뽑아봤다 (한국시각):

| 회차 | 종류 | 결과 | 시각 |
|---|---|---|---|
| 8 | 예약 | 성공 | 08-07 10:52 |
| 7 | 예약 | **취소** | 08-07 02:25 → 02:40 |
| 6 | push | 성공 | 08-06 20:26 |

**8/6 20:34 ~ 8/7 10:52 (14시간) 동안 예약이 딱 한 번 시도되고 그마저 취소됐다.**
30분마다면 28번쯤 돌았어야 한다. 7번 회차는 단계가 **하나도 시작되지 않은 채**
15분 대기하다 취소됐다 (실행기를 못 잡음).

그동안 사이트는 저장돼 있던 `2026-08-06 20:14` 짜리 파일을 계속 내보냈다.
→ 사용자가 새벽에 본 "같은 시각, 같은 내용" 이 정확히 이것이다.

**왜:** `cron: '0,30 * * * *'` 였다. 정각과 30분은 전 세계가 몰리는 시각이고,
GitHub 은 이때 밀린 예약을 **미뤄주는 게 아니라 그냥 버린다.**

**고침:** `deploy.yml` 의 cron 을 `'7,37 * * * *'` 로 옮겼다.

## 2. 원인 ② — 아이폰이 화면을 얼려둔다

`app.js` 의 검색어 읽기가 **페이지가 처음 열릴 때 한 번만** 실행되고 있었다.
아이폰은 홈 화면 앱을 껐다 켜도 새로 여는 게 아니라 재워둔 화면을 그대로 깨운다.
→ 그 코드가 다시 안 돌아서, 서버에 새 자료가 있어도 몇 시간 전 화면이 보인다.

**고침:** `loadTrends()` 로 함수를 빼고 `visibilitychange` · `pageshow` 를 달았다.
앱으로 돌아올 때마다 다시 읽는다. 1분 안에 이미 읽었으면 건너뛴다.

### 아닌 것으로 확인된 것 (다시 파고들지 말 것)

- **서비스워커 아니다.** `sw.js:35` 가 `/data/` 는 저장 안 하도록 이미 제대로 막고 있다.
- **브라우저 캐시 아니다.** 주소에 `?t=` 가 이미 붙어 있었다.
- **UTC 문제 아니다.** 8/6 에 고친 `UtcNow.AddHours(9)` 가 정상 동작 중이다.
- **서버 자료는 멀쩡했다.** 점검 시점에 `10:52` 기준으로 최신이었다.

## 3. 덤 — 얼마나 묵었는지 같이 보여준다

화면에 절대 시각만 나오면 10분 된 자료와 14시간 된 자료를 구분할 수 없다.
`08-07 10:52 (38분 전)` 처럼 나오게 했다. 이번 같은 상황을 바로 알아챌 수 있다.

시각 계산(`trendAge`)은 **12건 시험 전부 통과.** 자정 넘어가는 경우, 폰 시계가
앞선 경우, 값이 이상한 경우까지 포함했다. 이 PC 에 `node` 가 없어서 계산 부분만
떼어 윈도우 내장 `cscript` 로 돌렸다.

> `cscript` 로 한글이 든 `.js` 를 돌리려면 **BOM 이 있어야 한다.** `.ps1` 과 같은 사정이다.
