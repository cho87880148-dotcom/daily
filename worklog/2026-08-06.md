## 5. 로또

### 뽑기 기준을 두 번 고쳤다

처음엔 "32 이상 2개 이상"을 핵심으로 짰는데, 사용자가
**"너무 한쪽에 국한되지 않게, 쏠리지 않게"** 를 요청해서 균형형으로 다시 짰다.

구간 분산 / 홀짝 / 고저 / 합계 / 연속수 / 끝자리 / 32 이상 — 일곱 조건.
**무작위 조합의 50.07% 가 통과**한다 (3만 회 모의실험). 너무 빡빡하지도 헐겁지도 않다.
통과 조합의 합계 평균 138.1 로 이론 평균(138)과 일치 — 편향이 안 생겼다는 뜻이다.

> 검증 스크립트에서 `$N` 과 `$n` 이 **같은 변수로 취급돼** 결과가 깨졌다.
> PowerShell 변수는 대소문자를 안 가린다. 이미 CLAUDE.md 함정 3번과 같은 계열의 실수다.

### ★ 정직성 문구를 넣었다

사용자가 "확률이 조금이라도 높은 번호"를 원했다. 사실대로 나눠서 설명했다.

- **과거 패턴으로 다음을 맞히는 건 불가능하다.** 일곱 조건 중 여섯은 확률과 무관하다
- **32 이상 조건만 진짜다** — 확률이 아니라 **당첨금을 나눠 갖는 인원**을 줄인다

이 구분이 화면의 "읽어두세요" 칸과 뽑기 결과 마지막 줄에 그대로 적혀 있다.
**이 문구를 빼지 말 것.** 본인이 만든 도구라서 더 믿게 되는 게 이 앱의 유일한 실질적 위험이다.

### 당첨번호 자료는 못 받았다

동행복권이 JSON API(`common.do?method=getLottoNumber`)를 **막았다.**
JSON 대신 홈페이지 HTML 이 온다. `gameResult.do` 쪽도 마찬가지고,
User-Agent 와 세션 쿠키를 넣어도 안 된다. (2026-08-06 실측, 4가지 주소 시도)

`fetch-draws.ps1` 은 막힌 걸 감지하면 안내만 하고 안전하게 끝난다.
**자료가 없어도 앱은 정상이다** — 통계 칸만 안 보이고 합계 기준은 기본값 100~175 를 쓴다.

### ③ ★ 공 움직임을 CSS 에서 물리 계산으로 전면 교체

사용자 지적: **"일정 패턴으로 계속 왔다갔다만 한다"** — 정확한 지적이었다.
CSS 애니메이션은 `from`→`to` 를 반복하는 구조라 값을 아무리 흩어놔도
결국 정해진 길의 왕복으로 보인다. **CSS 로는 이 요구를 만족시킬 수 없다.**

`requestAnimationFrame` 으로 매 프레임 위치를 직접 계산하도록 바꿨다.

- 공마다 독립적인 속도·방향 벡터
- **매 프레임 무작위 바람** ← 경로가 반복되지 않는 핵심
- 원형 벽 반사(법선 방향), 마찰, 속도 상·하한
- 공끼리 탄성 충돌 — 45개면 매 프레임 990쌍

**추첨 중에는 목표 속도(`physTarget`)만 올린다.** 움직이는 방식은 동일하므로
사용자가 요청한 "그 패턴을 유지한 상태에서 공이 나오게"가 그대로 성립한다.
뽑힌 공은 `physBalls` 배열에서 빼고 나머지는 계속 돈다.

> 다른 탭으로 가면 `visibilitychange` 로 계산을 멈춘다. 안 그러면 배터리를 계속 먹는다.
> `prefers-reduced-motion` 을 켠 경우엔 물리 계산을 아예 돌리지 않는다.
